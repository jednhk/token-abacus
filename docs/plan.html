Token Abacus

Before an agent starts a task, tell it which model to use and what budget to set, based on what similar tasks actually cost other people. After the task, record what it really cost, automatically.

01Why

Nobody can predict what an agent task will cost. A solopreneur doesn't know whether "set up a reverse proxy" is a $0.40 or a $4 job. An agent running overnight has no realistic budget to work against, so it either stops too early or burns money.

Token Abacus is a shared database of real tasks: task, model, tokens, cost. Before a task, the agent asks it for a recommended model and budget. After the task, the real numbers go back in.

Who it's for

  • Solopreneurs and indie builders who want a cost number before they press go.
  • Agents running unattended that need a budget ceiling grounded in data.

How data gets in

  • Automatically, every task (main path). The local MCP server estimates before each task and uploads the real token counts after it.
  • Usage report (second path). Paste a prompt from the website into any coding tool and get a 30-day report; contributing that history is optional.
  • Manual submissions (stretch). A web form and leaderboard.

02Demo

What the judges see, in order:

  1. On a fresh machine, run npx token-abacus init. It reports "Added to Claude Code and Cursor" and asks whether to contribute data.
  2. In Claude Code, type "Set up a Caddy reverse proxy for my app." The agent first replies "Similar tasks cost about $0.40 on Sonnet (budget 180k tokens, 31 similar tasks)", then starts working.
  3. When it's done, the agent records the task. The dashboard shows the new row with exact token counts read from the session log, next to the estimate.
  4. On the website, paste the report prompt, get a 30-day usage report, contribute, and watch the database grow.

Why a local MCP server

At the end of a task, someone has to say how many tokens it used. The agent can't, because it doesn't see its own usage. A server running on the user's machine can read the coding tool's own session log and add it up exactly.

Why it's fast

The prompt is embedded inside the Edge Function with Supabase's built-in gte-small model, so there's no external API call. One database query finds the nearest tasks and computes per-model stats. Target: under 300 ms.

05How the estimate is made

StepRule
Find similar tasks50 nearest by meaning; keep similarity ≥ 0.80; drop flagged and pending rows
Candidate modelsAt least 3 similar tasks
Recommended modelCheapest median cost among models with ≥ 70% success, or the model the user is running
Budget85th-percentile tokens × 1.15: enough for about 85% of similar tasks, plus headroom
Ceiling95th percentile
ConfidenceHigh: ≥ 10 tasks, high similarity, p85 < 2 × p50. Low: few tasks or a wide spread
Too few matchesRetry with similarity ≥ 0.70 and mark confidence low

Percentiles use successful tasks only. Budgets are shown in dollars first and tokens second, because cache reads dominate raw token counts and dollars are what users understand.

06Data quality

  • Task boundaries come from the agent. One estimate_task plus one submit_run is one task. That gives small, specific rows like "set up Caddy" or "fix login bug", not whole sessions.
  • Token counts come from the session log, never from the agent. Count each requestId once and include subagent logs.
  • Text is the agent's one-sentence task and summary, scrubbed locally for keys, emails and paths. On the server, Haiku tags task_type and scope and does a second redaction pass.
  • Trust weights: automatic (MCP) 1.0, report 0.8, manual submission 0.3. Rows more than 10× or less than 0.1× the median of at least 5 similar tasks are flagged and excluded.
  • Model names are normalized to model_pricing keys, and cost is always computed on the server.

09Security, privacy and cost

  • Row-level security is on and clients never touch tables. All reads and writes go through Edge Functions, and database functions can't be called by anon or authenticated.
  • Only the task sentence, summary, model and token numbers leave the user's machine. Never code, file names, paths or log lines.
  • Contributing is opt-in at init. Estimates work without it.
  • Rate limits per install_id and per IP.

Secrets

SUPABASE_SERVICE_ROLE_KEY for Edge Functions only (provided automatically). ANTHROPIC_API_KEY as an Edge Function secret, for tagging. Clients need no keys.

Budget

Supabase Pro (about $25 a month) from the $100 credits, with the spend cap on. Haiku tagging costs a fraction of a cent per task and runs only on submit, never on estimate.

Local MCP server build guide

The local MCP server is the main product. It runs on the user's machine (npx token-abacus mcp), gives the agent two tools, estimate before a task and submit after it, and reads the coding tool's own session log so token counts are exact and never come from the agent.

M1One task, end to end

User: "Set up a Caddy reverse proxy for my app"
  │
  ├─► agent calls estimate_task({ task: "Set up Caddy reverse proxy with TLS for a Next.js app" })
  │     local server: create run (run_id, start time, session log) → save to state file
  │                   POST /estimate → "~$0.40 on Sonnet · budget 180k tokens · 31 similar"
  │
  ├─► agent does the work (normal tool use)
  │
  └─► agent calls submit_run({ run_id, outcome: "success", summary: "Configured Caddy with auto TLS" })
        local server: read session log from start → now, sum usage per model (exact)
                      POST /submit { summary, model, tokens, duration, outcome } → remove from state

Safety nets, so data is collected even when the agent forgets

SituationBehavior
Agent never calls submit_runThe next estimate_task closes the open run first, with outcome unknown
Session ends (server process exits)The shutdown handler closes and uploads the open run
Process killed before uploadThe run is still in the state file, so it's closed and uploaded on the next start
Upload fails (offline, server error)The payload goes to the outbox and is retried on the next start or call
API slow or down during an estimate3-second timeout; the tool returns "No estimate available" and the agent carries on

Stack

  • Node 20+ and TypeScript, published to npm as token-abacus. Check the name is free with npm view token-abacus.
  • @modelcontextprotocol/sdk with the stdio transport, and zod for tool input schemas, at the version the SDK's peer dependency asks for.
  • Build with tsup or tsc to dist/, with "bin": { "token-abacus": "dist/cli.js" } and a #!/usr/bin/env node shebang.
  • Keep runtime dependencies to a minimum, because npx start-up time matters.

M2Tools

estimate_task

Description"Get a cost and token-budget estimate for a coding task before starting it. Call this once at the start of each distinct task the user asks for. Describe the task in one specific sentence (what + stack), not the user's raw words. Skip it for questions and trivial one-step edits."
Inputtask: string (required, 10–300 chars) · model?: string (the model the agent is running as) · cwd?: string (absolute project path, used only locally to find the session log, never uploaded)
Behavior1. If a run is open, close it as unknown and queue its upload. 2. Create a run: run_id = crypto.randomUUID(), started_at = now, harness and log location; save state. 3. POST /estimate with a 3-second timeout.
OutputShort text for the agent, plus structuredContent with the full API response and run_id.
 
Estimate (run_id 6f1c…): ~$0.40 on claude-sonnet-5-5, budget 180k tokens (ceiling 290k), high confidence.
Based on 31 similar tasks, e.g. "Nginx reverse proxy with Let's Encrypt".
Tell the user the estimate in one line, then start. Call submit_run with this run_id when done.

submit_run

Description"Record a finished task so future estimates improve. Call this when the task you estimated is complete (or abandoned). Token counts are read automatically; do not include them."
Inputrun_id: string · outcome: "success" | "partial" | "failed" | "abandoned" · summary: string (one sentence on what was done, with no secrets, file contents or personal names)
Behavior1. Look up the run (an unknown id returns an error message, never a crash). 2. ended_at = now. 3. Read usage from the session log between start and end. 4. If contributing is off, drop it. 5. POST /submit. 6. Remove it from state.
OutputRecorded: 182k tokens, $0.37 on claude-sonnet-5-5 (estimate was $0.40).
Never put token counts in the input schema. The agent would guess them.

M3Server instructions

MCP servers can send instructions when they start. Clients that support it, including Claude Code, add them to the agent's context. Repeat the essentials in the tool descriptions for clients that don't.

const server = new McpServer(
  { name: "token-abacus", version },
  { instructions: `Token Abacus estimates what coding tasks cost.
- At the START of each distinct task the user asks for, call estimate_task with a one-sentence task description, and tell the user the estimate in one line.
- When that task is DONE (or abandoned), call submit_run with the run_id and a one-sentence summary.
- One task = one estimate_task + one submit_run. A new request from the user is a new task.
- Skip both for questions, explanations, and trivial one-step edits.
- Never send secrets, file contents, or personal names in task or summary.` }
);
stdio rule: never write to stdout except through the SDK, because it corrupts the protocol. Log to stderr or ~/.token-abacus/debug.log.

M4Reading token usage from session logs

Which client launched us: after initialization, server.server.getClientVersion() returns the client's name and version. Map it to claude-code, codex or other, and log the raw name the first time so we learn the real values.

Claude Code (checked against real logs, Oct 2026)

  • Location: ~/.claude/projects/<encoded cwd>/<sessionId>.jsonl, where the encoded cwd is the project path with every non-alphanumeric character replaced by -.
  • Subagent usage is in separate files at <encoded cwd>/<sessionId>/subagents/agent-*.jsonl. Include them.
  • Which session: the newest .jsonl in that folder. If the folder isn't found, scan files modified in the last hour for lines whose cwd matches. Resolve again at submit time.
  • One API response is written as several lines with the same requestId and identical usage. Count each requestId once. On a real sample, about a third of usage lines were repeats.
async function claudeUsage(files: string[], start: number, end: number) {
  const seen = new Set<string>();
  const byModel = new Map<string, Usage>();
  for (const file of files) {
    for await (const line of readLines(file)) {
      let e; try { e = JSON.parse(line); } catch { continue; }
      const u = e?.message?.usage;
      if (!u || !e.requestId || seen.has(e.requestId)) continue;
      const t = Date.parse(e.timestamp);
      if (t < start || t > end) continue;
      seen.add(e.requestId);
      const m = byModel.get(e.message.model) ?? { input: 0, output: 0, cacheRead: 0, cacheWrite: 0 };
      m.input += u.input_tokens ?? 0;
      m.output += u.output_tokens ?? 0;
      m.cacheRead += u.cache_read_input_tokens ?? 0;
      m.cacheWrite += u.cache_creation_input_tokens ?? 0;
      byModel.set(e.message.model, m);
    }
  }
  return byModel;   // primary model = most output tokens; send all models
}

Codex (verify against a real file first)

  • Location: ~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl; pick the newest whose session cwd matches.
  • Expected: token_count events with cumulative totals, and turn_context entries with the model. Usage for a run is the cumulative total at the end minus the total at the start.
  • Get a real rollout file from a teammate who uses Codex and add it to the test fixtures before relying on this.

Other clients

Cursor and others have no readable log yet. Submit with token_source: "none"; the server stores these as pending and leaves them out of estimates.

M5Local state and shutdown

File in ~/.token-abacus/Contents
config.jsoninstall_id, contribute flag, optional API override; written by init
state.jsonOpen runs keyed by run_id: task, start time, harness, cwd, log file, pid
outbox.jsonlSubmit payloads that failed to upload
debug.logLogs, capped at about 1 MB
  • Several sessions can run at once, one server process each. Key state by run_id, store the owning pid, write to a temp file then rename, and on start-up only auto-close runs whose pid is no longer alive.
  • Shutdown: the client closes stdin or sends SIGTERM/SIGINT. Handle all three: close this process's open run and try the upload with a 2-second timeout. If it doesn't finish, the run stays in state.json and is uploaded on the next start.
  • API: base URL defaults to the Supabase functions URL; override with TOKEN_ABACUS_API, and use mock for canned responses during development.

M7Privacy rules (enforced in code)

  • The only uploaded text is task and summary. Before sending, a local scrubber removes API-key patterns (sk-…, ghp_…, AKIA…, JWTs), emails, URLs with query strings and absolute paths, and truncates each field to 300 characters.
  • Never upload cwd, file names, file contents or log lines.
  • With contribute: false, estimates still work and nothing is submitted.

M9Test checklist

  • API down: the tool returns quickly with "No estimate available".
  • Two Claude Code sessions in different projects at once: each run reads its own log.
  • Agent never calls submit_run: the next estimate_task uploads the previous run as unknown.
  • kill -9 on the server mid-run: the next start uploads it.
  • A summary containing sk-ant-… and an email: both are stripped before upload.
  • contribute: false: no network call to /submit.
  • Nothing is printed to stdout outside the protocol.

—Glossary

Embedding, vector search
Turning text into numbers so "Caddy reverse proxy" and "Nginx reverse proxy" land close together. We look up the closest past tasks.
p50, p85, p95
The token count that 50%, 85% or 95% of similar tasks stayed under.
Edge Function
A small TypeScript server function hosted by Supabase.
MCP
The standard way agents (Claude, Codex, Cursor and others) call external tools. A local MCP server runs on the user's machine, started by their coding tool.
